# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

> **Working directory**: All commands below should be run from `nvs-maintenance/`.

## Commands

```bash
npm run dev        # Start Vite dev server (http://localhost:5173)
npm run build      # Production build → dist/
npm run lint       # ESLint
npm run preview    # Preview production build locally
npm run schema:dump  # Regenerate docs/schema.sql and src/types/database.types.ts
```

### DB change workflow (follow this every time, in order)
1. **Write the migration file** in `supabase/migrations/` — this is the source of truth and goes to git.
2. **Preview via MCP `execute_sql`** using a `BEGIN; ...; ROLLBACK;` wrapper — Claude verifies the output before anything is permanently applied. Raise it with the user only if something looks risky.
3. **Apply via MCP `apply_migration`** with the clean SQL (no BEGIN/ROLLBACK) — recorded in migration history, atomic.
4. **Regenerate** with `npm run schema:dump` — keeps `docs/schema.sql` and `src/types/database.types.ts` in sync.

> **`execute_sql` is never used to make schema changes directly** — always go through `apply_migration` so the change is tracked. `execute_sql` is for queries, data fixes, and previews only.

### Edge Functions
```bash
supabase functions deploy <function-name> --no-verify-jwt   # Deploy an edge function
# Functions: create-user, update-user, send-email, daily-digest, upload-to-drive, sync-roorides-vehicles, backup-to-drive
```

> All edge functions must be deployed with `--no-verify-jwt` — this project uses caller-identity checks inside the function code instead of gateway-level JWT verification.

## Architecture

### Stack
- **Frontend**: React 19, Vite 7, React Router 7, TanStack Query 5, Tailwind CSS 3, React Hook Form 7 — app source is `.jsx`, not TypeScript (only `src/types/database.types.ts` is auto-generated)
- **Backend**: Supabase (Postgres + Auth + Edge Functions)
- **Email**: Resend API (via `send-email` edge function)
- **File Storage**: Google Drive (via `upload-to-drive` edge function + service account)
- **Deployment**: Vercel (SPA, all routes rewrite to `/index.html`)

### What this app does
A fleet maintenance ticketing system for NVS Travel Solutions. Supervisors submit tickets → maintenance exec assigns and manages work via job cards → mechanics complete jobs → finance tracks costs.

### State Management
- **Auth state**: React Context via `useAuth()` hook (`src/hooks/useAuth.js`) — exposes `user`, `userProfile`, `loading`
- **Server state**: TanStack Query via custom hooks (`useTickets`, `useIssues`, `useJobCards`, etc.) — these are the single source of truth; mutations invalidate related query keys on success
- No Redux or Zustand

### Auth & Role Enforcement (two-tier)
1. **Database level**: Every table has RLS policies enforced by Postgres. Supervisors are scoped via `user_sites` junction table; `maintenance_exec` and `super_admin` have global access (the `is_maintenance_exec()` DB function covers both).
2. **React level**: `ProtectedRoute` in `src/App.jsx` checks `userProfile.role` against `allowedRoles`. Deactivated users (`is_active = false`) are forcibly signed out on profile fetch.

Roles:
| Role | Access |
|---|---|
| `supervisor` | Site-specific tickets/issues and outsource invoices (multi-site via `user_sites`; MAIN-141) |
| `maintenance_exec` | Global admin — job cards, issues, most settings |
| `super_admin` | Everything `maintenance_exec` can do + SLA rules, system_settings, holidays |
| `mechanic` | Assigned job cards only |
| `electrician` | Same scope as `mechanic` (job cards only) |
| `finance` | Finance entries, inventory, vehicles; read-only purchase invoices (MAIN-129) and job cards (MAIN-88) |

**Finance reads job cards through SELECT-only policies (MAIN-88).** `"Finance view job cards"` alone left a card's issues, parts, ticket numbers and mechanic name invisible, because each lives in its own RLS-protected table. Finance therefore also has SELECT on `issues`, `issue_parts` and `tickets`, plus `users` rows whose role is `mechanic`/`electrician` — all via `is_finance()`, which exists because a `users` policy that queries `users` recurses. Finance has no write path onto a job card; `JobCardDetail` shows the invoice details and file read-only to every non-exec (`invoiceReadOnly`).

**When adding a new role**, update: (1) `users_role_check` constraint in a migration, (2) relevant RLS policies / DB helper functions, (3) `ProtectedRoute allowedRoles` arrays in `src/App.jsx`, (4) `MANAGEABLE_BY` + `ROLE_LABELS` + `ROLE_COLORS` in `src/constants/userRoles.js`, (5) the role matrices in the `create-user` and `update-user` edge functions, (6) any role-conditional UI in pages/components.

### User Management (`/settings/users`)
`src/pages/Users.jsx` lists users with search + role filter. Creation goes through `AddUserModal`; `super_admin` additionally gets an Edit button per row (`EditUserModal`) covering name, email, role, employee ID, contact, assigned sites and an optional password reset. Both modals share `src/constants/userRoles.js` (role matrix, labels, colours, and `generatePassword()` — which produces readable `Mango-River-47` style passwords from `src/constants/wordlist.js`) and `SiteCheckboxList`.

Neither the edit nor the activate/deactivate toggle writes to `public.users` from the browser — both call the `update-user` edge function, so every change is role-checked server-side and recorded in `user_audit_logs`. That table is **super_admin-read-only with no INSERT policy** (only the service-role edge functions write to it), and is surfaced by the paginated `UserAuditLog` panel below the user list. Its `target_user_id` / `performed_by` columns are deliberately **not** foreign keys, and it snapshots names and emails, so history survives a user being deleted or renamed.

**Employee ID is mandatory and unique (MAIN-143).** `users.employee_id` is `NOT NULL` with no default (a default would quietly fill the blank the forms must refuse), and `users_employee_id_trimmed_check` refuses blank or space-padded values. Uniqueness ignores case, spaces and hyphens: the generated column `employee_key` (`lower`, spaces and hyphens removed) carries a unique index, so "NVS 1234", "nvs-1234" and "NVS1234" are one ID. `create-user` and `update-user` trim it, refuse a blank, and look up `employee_key` first to name the clash (`create-user` does this before the auth user exists, and deletes it if the index still catches a race); `employeeKey()` in `src/utils/employeeId.js` mirrors the column. The 14 users with no ID when this shipped were filled as `AUTO-1` … `AUTO-14` in `created_at` order and 3 leading tabs were trimmed — each logged in `user_audit_logs` as "System (MAIN-143)"; a super_admin replaces an AUTO ID in Edit User. The employee ID is also a mechanic's page address, so correcting one breaks any copy of the old link kept outside the app.

### user_sites & vehicle_sites Junction Tables
- `public.user_sites (user_id, site_id)` — supervisors may be assigned to multiple sites. The old `users.site` text column still exists for backwards compatibility but is no longer authoritative — RLS policies join through `user_sites`.
- `public.vehicle_sites (vehicle_id, site_name)` — vehicles may be assigned to multiple sites, surfaced on the Vehicles page.

### The `sites` table is machine-owned — do not add a UI for it
`sites` is not maintained by hand. It is a by-product of the Roorides vehicle feed: `sync-roorides-vehicles` splits each vehicle's `school` field and creates a row per distinct value.

**Rows are never deleted.** `tickets.site`, `job_cards.site` and `finance_entries.site` are free text with no foreign key, and `user_sites.site_id` has one, so deleting a site orphans history and breaks supervisor assignments. Departure is expressed as `is_active = false` instead.

**The sync owns `is_active` and rewrites it on every run** — a site is active exactly when the current feed still places a vehicle at it. The rule is two-way, so a site that regains vehicles reactivates itself, and a partial feed that wrongly deactivates one is corrected by the next run. Any UI that writes `is_active` would be silently overwritten within 24 hours, which is why there is deliberately no Sites settings page. `sites` also has no INSERT/UPDATE/DELETE RLS policy, so a browser client cannot write to it at all.

**`display_name` and `corp_id` are sync-owned too** — filled from `GET /api/ManageCorp/GetAllCorporation/0/0`, joined on `corpShortName`. They are display-only (`formatSiteLabel()` in `src/utils/siteLabel.js` renders `CODE — Full Name — corpId` for every site picker) and nothing matches on them, so that join is case-insensitive even though `name` is not. Both stay NULL when no corporation matches, and an unmatched site keeps its existing name rather than being reset. `DCTS` legitimately reads "Demo Corp" upstream; it is shown as-is by decision, not by bug.

Consequences worth knowing before touching site code:
- A site name is matched **exactly**, including case. The supervisor `SELECT` policy on `tickets` compares `tickets.site` against site names joined through `user_sites`, so a casing mismatch silently hides a supervisor's own tickets. In Aug 2026 an upstream rename (`Agrata` → `AGRATA`) left duplicate rows and cost a manual repointing of 7 assignments, 19 tickets and 17 job cards.
- Renaming a site means updating every one of those free-text columns **and** `user_sites` in the same transaction.
- Active-only is correct for *creating* a ticket and wrong for *filtering history* — a deactivated site's past tickets must still be filterable. See MAIN-50.

### Edge Functions (`supabase/functions/`)
All written in Deno/TypeScript. Each function uses `SUPABASE_SERVICE_ROLE_KEY` for admin operations (auto-provided by Supabase runtime). `create-user` additionally verifies the caller is a `maintenance_exec` by checking their profile via the anon key + caller JWT before proceeding.

| Function | Purpose |
|---|---|
| `create-user` | Provisions new users (auth + public.users profile). Requires `maintenance_exec` role. Writes a `CREATE` row to `user_audit_logs`. |
| `update-user` | Edits an existing user. Two modes via an `action` field: `update` (name/email/role/employee_id/contact/sites/password — **`super_admin` only**) and `set_active` (the activate-deactivate toggle — `super_admin`, plus `maintenance_exec` for supervisor/mechanic/electrician). Both write to `user_audit_logs`. Nobody may edit their own account through it. Email and password changes need the service-role key, which is why this can't be a client write. Note: a password change does **not** revoke the target's existing sessions. |
| `send-email` | Thin wrapper around Resend API for transactional emails |
| `daily-digest` | Reads `user_settings.notify_daily_digest` and sends personalised summaries via Resend |
| `upload-to-drive` | Uploads images to a specific Google Drive folder via service account JWT |
| `get-roorides-vehicles` | (Superseded) Early prototype — fetches vehicles from Roorides and returns them without persisting. No longer used by the app. |
| `sync-roorides-vehicles` | Authenticates with Roorides, fetches all vehicles for org 126 (via `ROORIDES_ORG_ID` secret), and upserts them into the local `vehicles` table. Never overwrites the `site` column. Called by pg_cron at midnight UTC daily and also manually via the "Refresh vehicle list" button on the ticket form. Credentials: `ROORIDES_USERNAME`, `ROORIDES_PASSWORD`, `ROORIDES_ORG_ID` secrets. **See the `sites` note below — the sync owns `sites.is_active`.** It owns `vehicles.is_active` the same way, and since MAIN-68 it is also the only thing that can create a vehicle at all — see the `vehicles` note below. |
| `seed-staging-from-prod` | **Staging only.** Replaces staging's public data and logins with production's. Requires `super_admin` role. Triggered via the "Seed Staging from Production" page under Settings (only visible when `VITE_ENABLE_DANGER_ZONE=true`). Secrets required in staging: `PROD_SUPABASE_URL`, `PROD_SUPABASE_SERVICE_ROLE_KEY`. **Staging ends up row-for-row identical to prod (MAIN-139)** — see below. |

Scheduled hourly 10 AM–7 PM IST (`30 4-13 * * *` UTC) via pg_cron (`nvs-hourly-backup` job). Secrets: `GOOGLE_SERVICE_ACCOUNT_EMAIL`, `GOOGLE_SERVICE_ACCOUNT_PRIVATE_KEY`, `BACKUP_DRIVE_FOLDER_ID`. |

**How the seed copies (MAIN-139).** Order: read prod's logins → `seed_truncate_public_tables()` (also restarts identities) → delete every staging login but the caller's → recreate prod's with password `NVSStaging2025!` → copy each table in FK order, prod reads paged by primary key (`seed_get_primary_keys`). The truncate must come before the login delete: 29 FKs to `public.users` and `user_settings → auth.users` have no delete action, so a login with history can't be deleted while its rows exist. Rows are written only through `seed_insert_rows(p_table, p_rows jsonb)`, which runs under `session_replication_role = replica` (no trigger fires, no FK is checked — Supabase allows it for `postgres`), inserts `OVERRIDING SYSTEM VALUE` so ticket / JC / MVI / PI / SUP numbers keep prod's values, leaves stored generated columns to recompute, and `setval`s each identity sequence to the copied max. A plain insert re-ran every trigger: stock was added twice, `issue_parts` was refused for "not enough stock", acceptance was re-judged and every running number was renumbered. **Never copy through PostgREST inserts again.** These functions exist on prod too, so every one that writes calls `seed_assert_staging()`, which refuses unless **Vault holds a secret `seed_target_environment` = `staging`** — created by hand on staging only; prod has none, so it fails closed. Recreate it after any staging rebuild: `select vault.create_secret('staging','seed_target_environment','MAIN-139 seed guard');`. All are service_role-only. The page shows "Sync complete" only when the response's `failures` list (tables and logins) is empty (`seedFailures`, `src/utils/seedResult.js`).

### Readable page addresses (MAIN-143)
Every record page is addressed by a number people can read, never by its uuid — long-ID links deliberately stop working:

| Page | Address | Built by |
|---|---|---|
| Ticket | `/tickets/1234` (`ticket_number`, unique by `tickets_ticket_number_key`) | inline `/tickets/${ticket_number}` |
| Job card | `/job-cards/3412` | inline |
| Multi-vehicle invoice | `/multi-vehicle-invoices/MVI-12` | `batchPath` |
| Purchase / refurbishment invoice | `/inventory?tab=history&invoice=PI-257` | `purchaseInvoicePath` (`src/utils/purchaseInvoice.js`) |
| Supplier | `/suppliers/SUP-5` | `supplierPath` (`src/utils/supplierNumber.js`) |
| Supplier statement | `/supplier-ledger/SUP-5` | `supplierLedgerPath` |
| Mechanic | `/mechanics/NVS-1234` (employee ID, spaces → hyphens) | `mechanicPath` (`src/utils/employeeId.js`) |

`purchase_invoices.purchase_number` (purchases and refurbishments share it) and `suppliers.supplier_number` are `GENERATED ALWAYS AS IDENTITY` like `job_card_number`; existing rows were numbered in `created_at` order before the identity was added, and the prod→staging seed copies them as prod has them (MAIN-139). **A page turns the readable value into the id once and then loads by id** (`useTicketIdByNumber`, `useSupplierIdByNumber`; `useMechanicProfile` matches `employee_key`; `usePurchaseInvoiceByNumber`), because every mutation's cache refresh is keyed on the id and every ledger function takes `p_supplier_id uuid`. So a link needs only the number: list queries fetch `ticket_number` / `purchase_number` / `supplier_number` / `employee_id`, `get_outsource_invoice_rows` puts `purchase_number` in its `purchase_invoice` block, the ledger lines carry `detail.purchase_invoice_number`, `get_supplier_balances` returns `supplier_number` and `get_labour_report` returns `technician_employee_id`. PI and SUP numbers are shown in Purchase History, the Edit Purchase / Edit Refurbishment header, the Invoices Reference column (beside the supplier's invoice number, which suppliers reuse), the supplier list and page, and the ledger list and statement.

### Sortable, filterable lists (MAIN-151)
Every list gets the same controls: each column header opens `ColumnMenu` (sort, then a tick list of the column's values with counts, or a "between" for dates and numbers), one search box above (`ListSearch`), a "Filtered by" strip (`ActiveFilters`), page controls and a session-only Columns button (`DataTable`, `src/components/shared/table/`). Sort, filters, search, page and the date range live **in the address** (`src/utils/listQuery.js`, tested: `f.site=BWIS&f.site=KUNS`, `min.value=…`, `from.raised_on=…`, `q`, `sort`/`dir`, `page`, `from`/`to`), so a reload or a shared link — and MAIN-152's Analytics drill-down — opens the same view. `useListState` (`src/hooks/useServerList.js`) owns it; the date range is always written into the address.
- **Big lists are sorted, filtered and paged by the database** (50 rows a page): Tickets, Issues and Job Cards call `get_ticket_list` / `get_issue_list` / `get_job_card_list(p_query jsonb)`, thin wrappers over one engine, `list_query(p_list, p_query)`, over `ticket_list_rows` / `issue_list_rows` / `job_card_list_rows(p_from, p_to)` (one jsonb per record in the IST date window; `_q` is the search text). All are **SECURITY INVOKER**, so row-level security decides the rows as before (supervisors: their sites). `p_query` carries `from`, `to`, `search`, `filters`, `sort`, `dir`, `page`, `page_size` (≤ 5000, Export pages through everything), or `facet` (one column's values with counts under every *other* filter). **Do not add a parameter** — add keys; MAIN-152 will add its Analytics selection the same way, joining `analytics_ticket_rows` / `analytics_issue_rows`. A new database-backed list = a `*_list_rows` function, a branch in `list_base_rows`, its name in `list_query`'s check, and a wrapper.
- **Date filters use the IST day** (`raised_on`), never a UTC timestamp's first ten characters; a column whose only date is a `timestamptz` (e.g. SLA Due) sorts but has no date filter.
- Cache keys start with the old keys (`['tickets', 'list', …]`, `['issues', …]`, `['job_cards', …]`), so every mutation's existing invalidation refreshes the lists.
- The Tickets page's status sections are now one-click shortcuts (`StatusShortcuts`), counted by the Status facet so they narrow with the list (MAIN-82). On a phone it shows the rows as `TicketCard`s with one "Sort & filter" button. Issues and Job Cards open on the current month, like Tickets.
- Small lists (Vehicles, Parts Catalog, Suppliers, Users, …) get the same controls in later stages, sorting what is already loaded in the browser and not paged. Supplier statements and company ledgers keep their recording order (running balances) — left alone until users ask.

### Key Data Model Relationships
- **Ticket** → has many **Issues** (category, severity, SLA tracking)
- **Issue** → optionally linked to a **Job Card** (`job_card_id` nullable)
- **Issue** → has many **issue_parts** (parts consumed during the repair)
- **Job Card** → assigned to a mechanic (InHouse) or vendor (Outsource)
- **Ticket** → has many **audit_logs** (grouped by `record_id = ticket_id`, covers ticket + issue + job card changes)
- **SLA** is calculated by database triggers from the SLA version the ticket and issue recorded (`sla_versions` + `sla_version_turnaround`, MAIN-136)
- **Part** → restocked via `purchase_invoice_items`; a DB trigger updates `parts.quantity_in_stock` on insert
- **purchase_invoices** → has many **purchase_invoice_items** → each references a `parts` row

### Issue categories (MAIN-140)
`issue_category` is an enum, mirrored by `src/constants/issueCategories.js` — keep them in step. AdBlue was renamed **Emission** with `RENAME VALUE`, so past issues read Emission too (old `audit_logs` text still says AdBlue). **Other is retired, not dropped** — 487 prod issues use it: `guard_issue_category` refuses adding an issue as Other or moving one to it (service-role writes pass), an existing Other issue keeps it, and a new SLA version has no Turnaround Time for it (`is_issue_category_retired()`, used by `sla_validate_change`; `sla_on_time_whatif` gives such issues their recorded days). Pickers offer `ISSUE_CATEGORIES` (`categoryOptions()` adds an issue's own retired category back); history filters use `ALL_ISSUE_CATEGORIES`.

### SLA System
SLA settings live in numbered versions (see **SLA versions** below), edited on the SLA Configuration page (`super_admin` can save everything, `maintenance_exec` holidays only). Database triggers auto-calculate `sla_end_date` and `sla_status` (Pending/Adhered/Violated) per issue. Working days skip the version's Weekly Offs and the `holidays` calendar. Timeline events are stored in `sla_events` and surfaced via `useSLAEvents(ticketId)` in `src/hooks/useSLA.js`.

**`resolved_at` / `closed_at` (MAIN-134).** `trg_stamp_ticket_resolved_closed_at` stamps `tickets.resolved_at` / `closed_at` (both `timestamptz`) when a ticket enters Resolved / Closed, and clears both when it leaves them (MAIN-135). Past tickets were backfilled from `audit_logs`. In the UI only unfinished tickets count down; finished tickets show the stored verdict.

**The SLA business rules (MAIN-135) live in one function, `refresh_ticket_sla(ticket_id)`,** called by every trigger and by the hourly pg_cron job `sla-hourly-refresh` (`refresh_overdue_slas()`, which also turns an overdue Acceptance SLA on a ticket with no issues to Violated), so a stored Pending is never more than an hour stale.
- **Deadline:** each issue's `sla_end_date` = the *ticket's* raise time + its Turnaround Time in working days, also for issues added later; the ticket's is the latest. Fixed by `calculate_issue_sla_dynamic` on insert / category or severity change and moved only by a holiday change (MAIN-136); `refresh_ticket_sla` never recomputes deadlines, only judges.
- **Activity complete time:** `issues.completed_at` (`timestamptz`), stamped on Done, cleared on leaving it, exec-correctable but never future (`set_issue_completed_on`). `completed_on` is kept in step as its IST date for the labour reports; a write of only `completed_on` becomes 00:00 IST. Every change is logged by the DB (`issue_completed_at_audit`, field `activity_complete_time`), so the app does not log it.
- **Verdicts:** an issue is judged at its `completed_at`; a ticket at the latest `completed_at` once every issue is Done (`sla_verdict()` — on or before the deadline is Adhered). A past Rejected ticket with issues, and its issues, are judged at `rejected_at`. **NA:** a ticket with no issues, and anything raised before SLA tracking — `is_sla_tracked()` (raised before 14 Aug 2026 00:00 IST; mirrored by `isSlaTracked` in `src/utils/slaStatus.js`). Pre-tracking deadlines stay NULL (MAIN-45).
- **Guards** (service-role writes pass, for the prod→staging seed): a ticket with issues can't be rejected; Closed and Rejected tickets take no new issues; a rated issue can't leave Done. Mirrored in the UI.
- **Status moves back:** an issue added to a Resolved ticket, or an unrated issue reopened, sends it to Work In Progress (`update_ticket_status_on_issue_change`). Deleting an issue re-evaluates both: the ticket is re-judged and its status follows the remaining issues (deleting the last unfinished one resolves it); a ticket left with no issues keeps its status and reads NA.

**SLA versions (MAIN-136).** Acceptance SLA Threshold, Weekly Offs and Turnaround Time (working days) are saved together as a numbered version in `sla_versions` (+ `sla_version_turnaround`, one row per category × severity), with who, why and a start time (now or a future date and time). A version ends when the next non-cancelled one starts — the end is derived (`versionTimeline` in `src/utils/slaDraft.js`), never stored. A **ticket** records the version active when it was raised (`tickets.sla_version_id`: its Acceptance SLA Threshold and Weekly Offs); an **issue** the version active when it was added (`issues.sla_version_id`: its Turnaround Time), so one ticket can mix versions. A category/severity correction recomputes with the issue's own version. **Changing a setting never moves an existing deadline.** Version 1 holds the settings in force when tracking began (14 Aug 2026) and every tracked ticket and issue was assigned to it; pre-tracking work has no version. A recorded version can't be changed except by the service role (`guard_sla_version_change`).
- **Only one version can be scheduled at a time.** A scheduled version can be cancelled with a reason before it starts, never edited; to change it, cancel it and save a new one.
- **Holidays are not versioned.** Adding or removing one (today or later, IST) moves every tracked deadline whose window covers the date — finished or not — and re-judges its statuses, acceptance included (`sla_holiday_effects`). Each change is logged in `sla_holiday_changes`. Maintenance execs may add and remove holidays too; a version change or cancel stays super_admin-only (`sla_assert_change_allowed`, called by both functions below).
- **Every write goes through `apply_sla_change(p_change jsonb)`** (`SECURITY DEFINER`, super_admin, or maintenance_exec for holiday-only changes; `action: 'cancel_version'` for cancelling), one reason per Confirm. `sla_versions`, `sla_version_turnaround`, `sla_holiday_changes` and `holidays` have SELECT policies only. A draft must start from the latest version (`STALE_DRAFT` otherwise). `preview_sla_changes` powers Review changes and writes nothing: the holiday effects, and on-time % for the last 30/90 days as it is and as it would have been (`sla_on_time_whatif` — per ticket, Turnaround and Acceptance separately, a ticket counted in the window its verdict was reached in). **Do not add a parameter** to either — the change travels as `jsonb` for the overload reason.
- `add_working_days(start, n, weekly_offs, holidays)` is pure: every setting is an argument, so the preview and the live triggers share one code path. `sla_rules_config`, the `system_settings` keys `acceptance_sla_days` / `sla_weekly_offs`, `acceptance_deadline()`, `recalculate_open_slas()` and the MAIN-45 recalculation triggers were dropped by MAIN-136 — don't re-add them.
- Service-role inserts (the prod→staging seed) keep the version and deadlines they supply.

> **There is no `sla_rules` table.** Two tables once held SLA day-counts: the settings page wrote `sla_rules` while the triggers always read `sla_rules_config`, so UI edits changed a row nothing consumed and the two drifted. MAIN-47 made `sla_rules_config` the single source and dropped the decoy (MAIN-136 later replaced `sla_rules_config` itself with `sla_version_turnaround`). Don't re-add `sla_rules` to anything — it lingered in `backup-to-drive`'s table list long afterwards, logging a failed read on every hourly run.

> **There is no SLA calculator in the browser.** `src/utils/slaCalculator.js` was a parked, unimported copy of the SLA rules; it was deleted under MAIN-43 (closed Won't Do) after MAIN-136 dropped every table and setting it read. A second copy of the rules in the browser is the drift behind MAIN-45, MAIN-47 and MAIN-134–136. Show the stored deadlines and statuses; an SLA figure the database doesn't store comes from a database function, as `preview_sla_changes` does for Review changes.

### Inventory Module
`src/pages/Inventory.jsx` (accessible to `maintenance_exec` and `finance`) has three tabs managed via local state:
1. **Parts Catalog** — stock levels, low-stock filter; `useUpdatePart` for inline edits
2. **Purchase History** — invoice list (`usePurchaseInvoices`), record new purchase via `PurchaseModal`; DB trigger auto-restocks parts when invoice items are inserted
3. **Consumption History** — `usePartConsumption`, shows parts used per job card/mechanic

**Purchase invoices are saved only through `save_purchase_invoice(p_invoice_id, p_invoice, p_items)` (MAIN-97).** Create (`p_invoice_id` null) and edit both go through it, so the header, line deletes/updates/inserts and `total_amount` commit or roll back together — the old five-call sequence left an invoice half-saved when a later line's stock check failed. It is `SECURITY INVOKER`, so the exec/finance RLS policies still decide who may save. It writes the header first so a workshop change moves the stock before any line changes (MAIN-72), and takes `total_amount` from the generated `line_total` column. Lines travel as `jsonb`: **do not add a parameter** — under `CREATE OR REPLACE` that creates a second overload rather than replacing it.

**The supplier comes from the approved list (MAIN-128).** Record Purchase, Edit Purchase and Record Refurbishment share `SupplierPicker` (approved suppliers, plus "+ Add supplier…" opening Quick Add with the typed name). `save_purchase_invoice` reads `supplier_id` from `p_invoice` and fills `supplier_name` from the supplier, so Purchase History keeps reading `supplier_name`. Invoices from before then have only a typed name: an edit that picks no supplier keeps it, while a linked invoice can't be unlinked, and keeping the same supplier skips the approval check so a later-rejected supplier doesn't block an edit.

**Every purchase invoice goes to finance (MAIN-129).** Record Purchase and Edit Purchase carry the outsource invoice details, and `save_purchase_invoice` writes the invoice's `outsource_invoices` row (the third owner, `purchase_invoice_id`) through `save_purchase_finance_invoice`, which `record_refurbishment` shares: the details are read from `p_invoice` (no new parameter), Invoice No and the date come from the purchase header so the two can't drift, and the lines must add up to the Approved Amount. Only `maintenance_exec`/`super_admin` save purchase invoices — the function checks, and the `purchase_invoices`/`purchase_invoice_items` write policies are exec-only; finance sees Edit Purchase read-only and has no Record Purchase. **The file is optional:** a purchase saved without it and with maintenance status Approved starts as **New (invoice pending)**, which finance can move only to Hold or Reject; the guard refuses Accepted (and New) while the purchase has no file, and uploading it in Edit Purchase moves the invoice to New under the `app.finance_submission` flag, so the history shows it. Once attached, a file can be replaced but not removed. **Accepted lock:** while finance has the invoice Accepted or GST-closed, `save_purchase_invoice` refuses any change but the notes, lines included. **Old invoices** — recorded before MAIN-129 reached prod, and so with no finance row — save exactly as before and never go to finance (they live in Google Sheets); the absence of the row is the definition, not `supplier_id` or a date. **Bulk Upload was removed (MAIN-147)** — invoices are recorded one at a time, with the file, when the bill arrives.

**Purchase and refurbishment forms (MAIN-130).** `purchase_invoices.kind` is `purchase` or `refurbishment`: `record_refurbishment` sets it under the transaction-local `app.recording_refurbishment` flag, and `guard_purchase_invoice_kind` refuses any other insert of a refurbishment and any change of kind (service-role writes, i.e. the prod→staging seed, pass). Every invoice opens through `PurchaseInvoiceEditor`, which picks `EditPurchaseModal` (lines, discounts, workshop) or `EditRefurbishmentModal` (each line's original → refurbished part, scrap source via `refurbishmentSource`, qty, price, GST, total and comment — shown, not edited; workshop shown) by kind — used by Purchase History's edit button and by `?invoice=PI-257`. What both share — supplier, notes, finance details, file, the finance badge, the Accepted lock, finance's read-only view, validation and the save — is `usePurchaseInvoiceForm` + `PurchaseInvoiceShared.jsx`, so the two cannot drift; both save through `save_purchase_invoice`, a refurbishment sending its lines back unchanged. Invoices reads the kind, and the ledger functions put it in `detail.purchase_invoice_kind`, so a line reads "Refurbishment" or "Purchase".

**Stock belongs to a company (MAIN-157, epic MAIN-154).** `part_stock` is keyed `(part_id, location_id, company)` — `nvs_travels` or `nvs_travel_solutions`; everything from before was NVS Travels. The only writer is `apply_part_stock_delta(part, location, company, delta)` (the three-argument version was dropped so a missed caller fails loudly). `purchase_invoices.billed_to` decides whose stock a purchase or refurbishment adds: required in Record Purchase, Edit Purchase and Record Refurbishment (`BilledToField`), carried inside `p_invoice` (no new parameter), locked with the other details under the Accepted lock, and changing it moves the invoice's stock like a workshop change (refused if some of it was used); a refurbishment's is fixed. `transfer_stock` lines carry `company` in `p_items` and stock arrives under the same company (Move Stock asks "Whose stock", one company per move). **Spares on a job card:** `deduct_part_from_inventory` (BEFORE INSERT) draws the vehicle's company's stock first (`job_card_stock_company()`) and records the split in `issue_parts.stock_draws` (`{"nvs_travels": 2, ...}`); removing the spare returns exactly that. An empty `stock_draws` on an in-house line means pre-MAIN-157, all NVS Travels. **The other company's stock only through a transfer (MAIN-159)** — see below. **Audits** count each company's stock separately: `stock_audit_items` is unique per `(audit, part, company)`, the count sheet has a **Belongs to** column (`parseBelongsTo` accepts only the two full company names; a found row must fill it), and `p_counts` / `set_stock_audit_reasons` items carry `company`; `stock_audit_movements` returns `company`, keyed client-side by `auditLineKey`. **Scrap** has `company`: from a job card, the vehicle's (`set_scrap_location_from_job_card`); from an audit, the counted line's. `record_refurbishment` refuses scrap of a company other than Billed to (`COMPANY_MISMATCH`), and its scrap picker lists only that company's. The Parts Catalog shows NVS Travels / Pvt Ltd columns per workshop and across all (`STOCK_COMPANIES`, `stockByCompany` in `src/constants/vehicleCompanies.js`).

**First-in-first-out cost and job card value (MAIN-158, epic MAIN-154).** Every quantity entering stock is a **lot**, per part and company across all workshops: a purchase or refurbishment line (by invoice date, under its Billed to; PI-176/180/183/185 make none — `is_workshop_move_invoice()`), stock found in an audit (at the part's latest cost), and an **opening lot** (`opening_stock_lots`) for stock that never came in on a recorded purchase — always first in the queue. What leaves stock — an in-house spare by its `stock_draws` split, or audit losses — takes the oldest lot left. Costs include GST (`(qty × price − discount) × (1 + GST %) ÷ qty`). `stock_cost_draws` holds which lot each spare took and is **derived**: `rebuild_part_cost(part, company)` deletes and recomputes a part's queue whenever a spare, purchase line, purchase header (Billed to / date), opening lot or completed audit changes it — so a corrected price, or an old bill entered late, re-costs every spare after it (user decision 2026-11-25). Never write `stock_cost_draws` by hand. The invariant, checked when it shipped: for each part and company, lots − taken = `part_stock` (`part_cost_gap()` = 0). The opening prices came from the "Opening stock prices" sheet (1zTbjY4o1zoa8huF_Hm5wlCIh4z_ZQOO_Fdq1a5yOJmU; 338 parts, quantity worked out at load, not taken from the sheet), and the costing uses only the app's own purchases, not finance's "Maintenance inventory 26-27" sheet (user decision). **Safety net:** a new spare whose stock has no lot is refused with HINT `PART_NEEDS_PRICE` (part, company and quantity in DETAIL); `IssueWorkCard` then shows `PartPriceModal` to an exec, which calls `add_opening_stock_price(p_part_id, p_price jsonb)` (exec/super_admin; prices every company's unpriced quantity once) and adds the spare again — **do not add a parameter**. **Value** (`job_card_value(job_cards)`, `spare_cost(issue_parts)` — PostgREST computed fields read as `value:job_card_value` / `cost:spare_cost`, NULL for anyone but exec, super_admin and finance): in-house = its spares' cost (₹0 with none, NULL = a price missing); outsourced = its invoice's Approved Amount, else its linked multi-vehicle invoice lines (cancelled ones out), else NULL ("Invoice pending"). Shown in the job card list's Value column, under the job card's title and beside each spare; wording in `src/utils/jobCardValue.js` (tested). A spare transfer's amount is frozen when posted (MAIN-159), and `spare_cost` / `job_card_value` use it for the transferred quantity.

**Spare transfers (MAIN-159, epic MAIN-154).** A spare takes what the vehicle's company holds at the workshop and the rest — if the other company holds it — only through a confirmed transfer (user decision 2026-11-25). The app adds spares through `add_spare(p_spare jsonb)` (`SECURITY DEFINER`, exec/super_admin; `{ issue_id, part_id, quantity_used, confirm_transfer?: { amount } }` — **do not add a parameter**). Without `confirm_transfer`, a spare needing the other company is refused with HINT `NEEDS_TRANSFER` and the quote in DETAIL (quantity per company, first-in-first-out cost incl. GST, GST per rate of the lots it took — `spare_transfer_quote()`, worked out by adding the spare in a subtransaction that is rolled back); `IssueWorkCard` shows `TransferSpareModal` and sends the amount back. If the quote no longer matches it is refused with `TRANSFER_CHANGED` and the new quote (`transferQuoteError`, `src/utils/jobCardValue.js`). The trigger lets the other company's stock through only under the transaction-local `app.spare_transfer` flag that `add_spare` raises, so a direct insert needing it is refused too; service-role writes draw both as before (seed, MAIN-160). `spare_transfers` (SELECT for exec/finance only; `issue_part_id` deliberately not a foreign key, part / job card / vehicle snapshotted) holds the frozen amount, GST and `gst_breakdown`; a transferred spare can't be updated (`guard_transferred_spare`), and removing it marks the transfer **Reversed** (BEFORE DELETE `reverse_spare_transfer_on_delete`), never deleted. The job card reads it as `transfer:spare_transfer` ("Transferred from …"; amount NULL for anyone who can't see costs). In the company ledgers a transfer moves **Spent to date** — the vehicle's company +amount, the supplying company −amount — and **Owed between companies** both ways, GST signed with the spending; a reversal is its own line on the day the spare was removed (`spare_transfer_*` kinds; user decision 2026-11-25 — vehicle sales stay Owed only). **Backfill (MAIN-160).** Spares from before MAIN-159 got transfers with `source = 'backfill'`, one per spare line, dated at the spare's `added_at`, posted by `post_backfill_spare_transfers(registration)` (371 lines on Pvt Ltd vehicles in prod). A job card's company is `vehicle_company_at(reg, jc.created_at)`: the latest sale on or before then, else the vehicle's **first** recorded company (initial load or first assignment), which counts from the beginning — not `job_card_invoice_company()`, whose "none before = NVS Travels" would post nothing. An Unknown vehicle's spares are posted by `trg_backfill_transfers_on_assignment` when finance first assigns it (to NVS Travels that posts nothing). **Backfilled amounts are not frozen:** `rebuild_part_cost` ends by calling `refresh_backfill_transfers`, so they follow their spare's cost (user decision 2026-11-25); live transfers stay frozen. Both quotes read `spare_draw_quote(issue_part, from_company)`. **Invoice transfers** are derived, not stored: a job card invoice whose `company` differs from its card's (pre-go-live, MAIN-161) adds `invoice_transfer_in` / `invoice_transfer_out` lines to `company_ledger_lines` for its Approved Amount while finance has it accepted (JC 1838 on KA51AJ3479 the one prod case). Backfilled and invoice transfers stay on their real past dates (user decision 2026-11-25), so assigning an old Unknown vehicle or an old bill re-costing a spare can move a figure finance already reconciled — finance then re-reconciles, as in Tally. Don't "fix" this by dating them on the day they are posted. The user is asking finance to assign the Unknown vehicles and to get MAIN-168's bills entered before the first company-ledger reconciliation.

**Part names are unique (MAIN-148).** Two names are one part when they match ignoring capitals and extra spaces (`part_name_key()`: lower case, trimmed, runs of spaces made one). The generated `parts.name_key` column carries a unique index, so the rule binds every writer — Record Purchase, Edit Purchase, Record Refurbishment and an outsourced job card's work item (new part), Parts Catalog edit (rename) and `record_refurbishment`'s automatic name — and the prod→staging seed skips the column and recomputes it. The screens check as the name is typed (`findSameNamePart`, `src/utils/partName.js`, mirroring the key) and show "Already in the catalog as '<name>' — use that one" via `DuplicatePartNotice`, with a button that picks the existing part (none on a rename); a refusal from the index (`23505` on `parts_name_key_key`) shows the same message. The 9 duplicate sets prod had were merged by the MAIN-148 migration: oldest copy kept, every reference moved to it (purchase lines with their stock triggers disabled), stock added per workshop, checked identical before and after, and logged in `audit_logs` (`merged_by: MAIN-148`). The same migration cleared the meaningless Part No. "1" from the 29 Jul 2026 upload on parts and scrap rows.

### Vehicles Page
`src/pages/Vehicles.jsx` — list + edit for the `vehicles` table (accessible to `maintenance_exec`, `super_admin`, `finance`). Search, site-filter via `vehicle_sites` join, and an inline **edit-only** modal. Uses `useVehicles` and `useUpdateVehicle` from `src/hooks/useVehicles.js`. Vehicles are synced nightly from the Roorides API via the `sync-roorides-vehicles` edge function.

**`vehicles` is feed-owned and has no create path — like `sites`, but with an edit UI.** Since MAIN-68 a vehicle can only be created by `sync-roorides-vehicles`. There is no Add Vehicle button, no `useCreateVehicle` hook, and the RLS policy `"Exec and finance update vehicles"` is **UPDATE-only**, so a browser client cannot INSERT or DELETE a vehicle even by calling PostgREST directly. Anything missing is fixed at source in Roorides. The only writer that can create rows is the sync itself, which uses the service-role key and bypasses RLS. Rows are never deleted (`tickets.vehicle_number` and `job_cards.vehicle_number` are free text, so history survives regardless) — departure is expressed as `is_active = false`.

The old `FOR ALL` policy was named `"Exec and finance manage vehicles"`; MAIN-68 dropped and recreated it under the new name, because `ALTER POLICY` cannot change a policy's command and the schema's convention is that `manage` denotes `FOR ALL` while `update` denotes `FOR UPDATE`.

**Only `year` and `notes` are editable.** Every other column — `registration_number`, `make`, `model`, `type`, `is_active`, `raw_data` — is rewritten by the sync on every run, so a local edit to one would be silently reverted within 24 hours. The edit modal therefore shows make/model, site and status read-only and offers inputs for year and notes alone. Note RLS gates rows, not columns: an exec could still PATCH a sync-owned column directly against PostgREST. The UI does not offer it and the sync corrects it nightly, which is the same posture `sites` has.

**`is_active` is sync-owned and not user-editable.** A vehicle is active exactly when the current Roorides feed still returns it — the same two-way rule `sites` gets. The Edit modal had an Active checkbox until MAIN-68 removed it: MAIN-69 made the column machine-owned, so any toggle was reverted by the next sync. This is the same failure mode that is the stated reason there is no Sites settings page. Before MAIN-69 nothing ever revisited the flag, so a vehicle that left the feed kept `is_active = true` forever while `vehicle_sites` was rebuilt without it — leaving 69 rows in prod that no supervisor could see (their vehicle list is site-filtered) but every exec could still pick (a blank Site field means an unfiltered list).

Feed-owned means `raw_data IS NOT NULL`. MAIN-69's `is_active` rule still filters on it, and MAIN-68 deliberately kept that filter: with no create path it is a harmless no-op, and removing it would only cost the guard if a manual row ever reappeared. The carve-out originally existed to protect two hand-added rows in prod (`KA-01-AB-1234`, `KA-01-AB-5678`) — both build placeholders created 2025-12-27 with zero tickets, zero job cards and no `vehicle_sites` links, retired under MAIN-68. No hand-added vehicle can exist from here on.

### Scrap / Salvage Module
`src/pages/Scrap.jsx` (`/scrap`, accessible to `maintenance_exec`, `super_admin`, `finance`) — tracks scrap/salvage parts and their disposal. Three tabs via local state: **Scrap Inventory**, **Sale History**, **Write-off History**. The record actions (`RecordSaleModal`, `RecordWriteoffModal`) are hidden for the `finance` role, which is view-only here (`isExec = role !== 'finance'`). Sales are recorded against the `scrap_disposal` table (buyer, payment mode/reference, total value, receipt photos). Tab + modal components live in `src/components/scrap/` (`ScrapInventoryTab`, `SaleHistoryTab`, `WriteoffHistoryTab`, `RecordSaleModal`, `RecordWriteoffModal`).

**Scrap defaults live in the part master.** A part can carry `default_exclude_from_scrap` + `default_exclusion_reason` (set via the checkbox column in the Parts Catalog, or from the closure modal — see below). `ScrapDecisionModal` seeds those rows as "Exclude from scrap" with the reason pre-filled and collapses them to a single line with a "Default" badge, so consumables need no interaction at closure. The exec can still override per job card; overriding never writes back to the part. The reason is constrained to `consumable` / `destroyed_on_removal` (`parts_default_exclusion_reason_check`) — `other` would need a per-exclusion note the part master cannot supply, and would pre-fill a state the RPC's `MISSING_EXCLUSION_NOTES` guard rejects. Reason labels are single-sourced in `src/constants/scrapExclusion.js`; keep `DEFAULT_EXCLUSION_REASON_OPTIONS` in step with the DB constraint. Each exclusion decision carries `from_default`, stored on `scrap_excluded_parts.from_part_default` — descriptive telemetry only, nothing reads it to make a decision.

**Defaults can also be set from the closure modal, and that write is server-side.** A decision may carry `set_as_default` or `clear_default`, and `close_job_card_with_scrap` updates `public.parts` inside the closure transaction — a client write after the RPC returned could leave a standing default behind on a closure that failed. Ticking any of those checkboxes routes Confirm-and-Complete through a second confirmation listing every affected part, because a part default outlives the job card it was set from. The RPC returns `part_default_changes` (real changes only, no-ops omitted) purely so the client can write the `parts` audit rows; nothing else reads it. Offers are keyed by **part**, not by `issue_part` — a part can appear on one card twice and can only carry one default, and the RPC rejects contradictory directives with `CONFLICTING_PART_DEFAULTS` rather than letting payload order decide. **Do not add a parameter to `close_job_card_with_scrap`** — the new fields live inside the `p_scrap_decisions` jsonb precisely so the signature stays a single 4-argument version; adding a parameter under `CREATE OR REPLACE` creates a second overload instead of replacing the first, which is how the orphan MAIN-57 had to drop came about.

**Stock-audit damage reaches scrap (MAIN-123).** A mismatch is explained by lines in `stock_audit_item_reasons` (quantity, reason, comment) that must add up to the absolute variance before `complete_stock_audit` runs; `stock_audit_items.reason`/`reason_notes` are superseded. Completion creates one `scrap_inventory` row per Damaged line, at the audited workshop, unless the part has `default_exclude_from_scrap`. So a scrap row now has exactly one source — a job card or `source_audit_reason_id` (`scrap_inventory_one_source_check`) — and its job card, ticket, issue and vehicle columns are NULL for an audit row.

**Refurbishment (MAIN-123).** `record_refurbishment(p_invoice, p_lines)` writes an ordinary purchase invoice whose lines add stock to `"<name> (Refurbished)"`, one catalog part per refurbished name via `refurbished_part_links` (keyed by the original; since MAIN-148 an existing part already carrying the refurbished name is reused, so originals of one name share it) (a table, not a self-reference, because the prod→staging seed cannot order a table's rows against each other). So the invoice appears in Purchase History and its cost becomes the audit valuation. Each line takes all or part of a scrap row: a partial line leaves the remainder on the original row and inserts a second `refurbished` row with the same sources, because sale and write-off only take whole rows. That means one `source_issue_part_id` can have an `in_storage` and a `refurbished` row at once; the part counts as permanently handled at job card closure, and `useExistingScrapForJobCard` ranks accordingly. A line with no `scrap_inventory_id` is a part that was never recorded as scrap — excluded at closure but physically in the scrap room — needs a comment, and shows "Scrap source details missing"; misuse was judged harmless, so nothing else restricts it. `guard_refurbishment_invoice_line` refuses changes to those lines, since that would move stock while the scrap stayed marked refurbished; `guard_refurbishment_invoice_new_line` refuses adding one (only `record_refurbishment` may, MAIN-130); `guard_refurbishment_invoice_header` does the same for the workshop; its other details are edited like any purchase invoice's (MAIN-129). Its arguments are `jsonb` — **do not add a parameter**.

**A refurbishment's invoice goes to finance (MAIN-123).** The supplier is chosen from the approved list (`purchase_invoices.supplier_id`; `supplier_name` keeps its name for Purchase History), with Quick Add prefilled from the typed name. The form takes the outsource invoice details through `InvoiceDetailsFields`, the file is required, and the parts must add up to the Approved Amount exactly (`AMOUNT_MISMATCH`, compared in `numeric`; `approvedAmountError` in paise on the client). `record_refurbishment` then inserts an `outsource_invoices` row with `purchase_invoice_id` set — the third owner `outsource_invoices_one_owner_check` allows — which is submitted to finance at once, like an MVI. From there the statuses, history, Accepted lock, summary tiles, supplier ledger and Advances to repay work unchanged; the ledger functions take the supplier as `coalesce(jc.supplier_id, bs.supplier_id, pi.supplier_id)` and mark the line with `detail.purchase_invoice_id`. A purchase invoice has no page, so Invoices and the ledger link to `/inventory?tab=history&invoice=PI-257` (`purchaseInvoicePath`, MAIN-143), which opens it in the form for its kind (MAIN-130). MAIN-129 extended this to every purchase invoice — see below.

### Invoices
`src/pages/OutsourceInvoices.jsx` (`/invoices`, accessible to `maintenance_exec`, `super_admin`, `finance`, `supervisor`) — finance's review of every invoice that reaches it: job card, multi-vehicle, purchase and refurbishment. Uses `useOutsourceInvoices` + `useOutsourceInvoiceSummary` from `src/hooks/useOutsourceInvoices.js`; the table's parts and the drawer live in `src/components/outsource-invoices/`.

**Who can read an invoice (MAIN-141).** One rule, `can_read_outsource_invoice(job_card_id, batch_service_id)` (SECURITY DEFINER): exec, super_admin and finance read every invoice; a supervisor reads the invoices of their own `user_sites` sites, every detail and the history included; mechanics and electricians read none. An invoice has no site of its own: a job card invoice takes `job_cards.site`, a multi-vehicle invoice is visible whole — every line — if **any** line's `batch_service_vehicles.site` is theirs, and a purchase invoice (a workshop's, not a site's) never is. Names match exactly, case included. The same rule is the table's only SELECT policy (`"Readers view their outsource invoices"`) and is applied inside every definer function that reads invoices for the page — `get_outsource_invoice_rows`, `get_outsource_invoice_summary`, `get_outsource_invoice_history` — because a definer function bypasses RLS. **Supervisors still cannot read `job_cards`, `batch_services`, `batch_service_vehicles` or `suppliers`** (suppliers holds bank and PAN details; opening `job_cards` would also fill the job card embed on their ticket screens), so the list comes from `get_outsource_invoice_rows(p_filters jsonb)` for every role rather than a PostgREST embed: it returns the embed's shape with the supplier's name only, plus a `total` for paging. Its argument is `jsonb` — **do not add a parameter**. Supervisors have no job card or MVI page, so `InvoiceCell` shows those numbers as plain text for them (`canOpen`).

**Company (MAIN-161, epic MAIN-154).** Every invoice stores whose it is in `outsource_invoices.company` (`nvs_travels` / `nvs_travel_solutions`), set on every write by the `outsource_invoices_set_company` trigger, never by hand: a purchase or refurbishment takes its `billed_to`, a multi-vehicle invoice its `batch_services.billed_to` (both followed when they change, by `sync_invoice_company_from_owner`), and a job card invoice the company its vehicle had **when the card was opened** (`job_card_invoice_company()` — the latest `vehicle_company_changes` row at or before `job_cards.created_at`; none = NVS Travels), kept from then on, so a sale after the work moves nothing. Every invoice from before MAIN-161 is NVS Travels and **stays NVS Travels even when its vehicle is first assigned to Pvt Ltd** (user decision 2026-11-25: NVS Travels paid those suppliers; job card 1838 on KA51AJ3479 was the one prod case). A multi-vehicle invoice's **Billed to** is required (`BilledToField`, inside `p_batch` — no new parameter), the vehicle picker greys the other company's vehicles, and `save_batch_service_invoice` refuses a vehicle of the other company (`COMPANY_MISMATCH`) — checking only new lines, lines whose vehicle changed, or every line when Billed to changes, so a vehicle sold after the work never makes an old invoice uneditable (`wrongCompanyLines`, `src/utils/batchCompany.js`, mirrors it). The Invoices page has a **Company** column and filter (`co` in the URL); `get_outsource_invoice_rows` takes `company` in `p_filters` and `get_outsource_invoice_summary` `p_company`, so the tiles follow it.

**GST breakdown (MAIN-166).** A job card or multi-vehicle invoice records its GST in `outsource_invoices.gst_breakdown` — `[{rate, before_gst, gst, incl_gst}]`, one row per rate, whose `incl_gst` add up to the Invoice Value exactly (`gst_breakdown_problem()`, mirrored by `gstBreakdownProblem` in `src/utils/gstBreakdown.js`; within a paisa of before × rate). Rates come from `gst_rates()` (0, 5, 12, 18, 28, 40), mirrored by `GST_RATES` in `src/constants/gstRates.js`, which Record Purchase, Edit Purchase and Record Refurbishment share (`gstRateOptions` adds a saved rate back if it ever leaves the list). The exec types Amount before GST or incl. GST and the rest is worked out (`GstBreakdownFields`, through `InvoiceDetailsFields gst`); the form passes `{ gst: true }` to `validateInvoiceForm` / `invoiceFormToRow`. `guard_invoice_gst_breakdown` refuses any user write of a job card / MVI invoice without a valid breakdown, except one that leaves an old invoice's details alone (finance's status and remark), and refuses a breakdown on a purchase (its GST is on its lines). It travels in the job card upsert, inside `p_invoice` for `save_batch_service_invoice` and inside `p_resubmission` (no new parameters); `finalize_outsource_invoice` and `complete_invoice_resubmission` require it, `outsource_invoice_snapshot` includes it so a GST-only fix counts as a resubmission change, and `log_outsource_invoice_change` logs it. Being a column on the invoice, the Accepted / Reject lock covers it. The 5 job card invoices from before have none: a Completed card shows **Add GST breakdown** (`AddGstBreakdown`) to execs until finance accepts or rejects it; finance may accept one without, and it then reads "Not recorded". The Invoices page's **GST** column is the bill's GST (`get_outsource_invoice_rows` → `gst`: a purchase's from its lines); the company ledger scales it to the Approved Amount.

**Two statuses, two owners (MAIN-90).** `maintenance_payment_status` (`Approved`/`Hold`/`Reject`, labelled "Payment status reported by maintenance") is the exec's decision on the job card closure form; it was called `payment_status` until MAIN-90. `finance_payment_status` and `finance_remark` are finance's, labelled "Finance status" (the column kept its name when MAIN-118 changed its meaning, rather than rewrite every stored history row and the prod→staging sync). Neither overwrites the other. Ownership is enforced by the `guard_outsource_invoice_status_owners` trigger rather than RLS, because RLS gates rows, not columns, and exec, finance and supervisor all hold UPDATE on the table: only `finance` and `super_admin` may change the finance columns, `finance` may not change the maintenance one, and service-role writes (NULL `auth.uid()`) pass. Both value lists live in `src/constants/outsourceInvoices.js` and mirror their CHECK constraints. `get_outsource_invoice_summary` takes `p_maintenance_payment_status` and `p_finance_payment_status` by name; changing its parameters or return columns needs `DROP` + `CREATE`, because `CREATE OR REPLACE` cannot and would leave a second overload behind.

**Finance statuses (MAIN-118).** Finance pays suppliers against a supplier ledger by credit period, not invoice by invoice (UAT, 2026-11-02), so MAIN-95's per-invoice payments — `outsource_invoice_payments`, its RPCs, the Due/Partly Paid/Paid recalculation and the payment strip — were dropped; supplier payments are MAIN-119's. Finance's status is now a review: **New** → **Hold** / **Reject** → **Accepted** → **GST reconciled & closed** / **GST not applicable & closed**, plus **New (invoice pending)** for a purchase invoice still waiting for its file (MAIN-129 — see the Inventory module). The guard allows only New ↔ Hold, New/Hold/Resubmitted → Reject or Accepted, Resubmitted → Hold, and Accepted → Hold, Reject or either GST close (`FINANCE_STATUS_MOVES` mirrors it for the dropdown). **Reject and both GST-closed statuses are final** — Reject leaves only by resubmission (MAIN-120, below); these are integrity rules, so they bind super_admin too. Every move into Reject needs a new reason in `finance_remark` in the same write (`RejectInvoiceModal` asks for it and warns it is final; `outsource_invoices_reject_reason_check` keeps it non-empty). **Accepted lock:** while the status is Accepted or GST-closed the guard refuses any change but finance's status and remark, the job card's Reopen is disabled and the MVI can't be saved or cancelled (`BATCH_LOCKED`, `BATCH_ACCEPTED`); moving back to Hold lifts it (`isLockedByFinance`); Reject keeps it locked until resubmission. **Submission:** `submit_outsource_invoice_to_finance` stamps `submitted_on` (IST) and sets the starting status from maintenance's — Approved → New, Hold/Reject → the same with the remark "Hold set by maintenance exec" / "Reject set by maintenance exec". It runs once, from `job_cards_submit_outsource_invoice` (card becomes Completed — closure and finalize alike) and `outsource_invoices_submit` (an MVI's first save, or an invoice added to an already-Completed card), raising a transaction-local `app.finance_submission` flag the guard lets through. A card reopened and closed again keeps its date and finance's status; a later maintenance-status change shows in the history without moving finance's status. `submitted_on` is where MAIN-119's due dates count from.

**Resubmission (MAIN-120).** A rejected invoice — by finance, or by maintenance at closure — is locked like an accepted one, for every owner type, and resubmission by `maintenance_exec`/`super_admin` is the only way through. The lock is enforced in the database for any writer, not just the UI: `guard_outsource_invoice_status_owners` refuses changes to the invoice row, and `guard_locked_invoice_details` (triggers on `job_cards` file/supplier, `purchase_invoices` everything but notes, and `purchase_invoice_items`) refuses changes to the owner's details while the invoice is Reject, Accepted or GST-closed — closing a direct-API gap the Accepted lock had. A batch's tables have no client write policies, so `save_batch_service_invoice` holds the rule there (`BATCH_REJECTED`). Two entry points: `resubmit_outsource_invoice(p_invoice_id, p_resubmission jsonb)` (`SECURITY DEFINER`; the Resubmit popup `ResubmitInvoiceModal`, from the list's Resubmit button and the job card page — file, supplier and invoice fields, with a purchase's number and date written to its header), and `save_batch_service_invoice` / `save_purchase_invoice` with `resubmit: true` and an optional `resubmit_note` **inside `p_invoice`** (line changes, on the MVI page or in Edit Purchase, where Save becomes "Resubmit to finance"; no new parameter, for the overload reason). Both raise the transaction-local `app.invoice_resubmission` flag, which the guards let through like `app.finance_submission`, and end in `complete_invoice_resubmission`, which refuses unless the flag is up, the invoice is Reject, maintenance's status is Approved or Hold, the file is there, any lines add up to the Approved Amount, and something changed — compared with `outsource_invoice_snapshot` (fields, supplier, file, lines) taken before the edit. It then sets the starting status as first submission does — Approved → **Resubmitted** with the remark cleared, Hold → Hold with "Hold set by maintenance exec" — and resets `submitted_on` to today, so the credit period restarts. A refurbishment's lines and workshop stay locked by their own guards. Resubmitted counts in the New tile and in `get_supplier_balances.awaiting_acceptance`; the popup's rules mirror the database in `resubmission.js`. Cancel/Restore of a rejected MVI still work.

**Invoice history (MAIN-96).** Trigger `outsource_invoices_audit` writes every change to `audit_logs` — the invoice's person-decided fields (both statuses, finance remark, Paid By, the three amounts, and the pay-by date while it was asked for) and `submitted_on`, so the submission shows as one entry with any starting status and remark; not timestamps. Being a trigger, it captures the closure form, the table cells, the submission and direct API calls alike. The drawer reads it through `get_outsource_invoice_history`, which attaches performer names (finance cannot read exec/finance profiles) and, for invoices created before the history existed, synthesises a "Created by" entry from the row itself. Staging still holds `audit_logs` rows for the dropped payments; nothing reads them. A resubmission is **one** entry (MAIN-120): the per-row invoice and batch-header logging is skipped while `app.invoice_resubmission` is up, and `complete_invoice_resubmission` writes a single `UPDATE` row whose `new_data` carries `resubmitted: true`, the note, and old/new of every changed field (`invoice_file`, `supplier_id` with `supplier_name`, `lines` named but not copied) plus the status and `submitted_on`. `audit_logs_action_check` allows only INSERT/UPDATE/DELETE, hence the marker rather than a new action. `groupBatchLines` turns it into a "Resubmitted by" entry and folds that save's MVI line changes into it. The earlier reject reason stays in its own entry.

**Edits happen in the table; the drawer shows history only (MAIN-98).** Finance and super_admin change Finance Status (`FinanceStatusCell`, saves on pick, offering only the allowed moves; a final status is a badge) and Finance Remark (`RemarkCell`, Enter/blur saves, Esc cancels) in their cells. `useUpdateFinancePaymentStatus` writes only the fields it is given, so the two cells cannot overwrite each other. The summary tiles count New (with Resubmitted) / Invoice pending / Hold / Reject / Accepted, and each is a shortcut to its Finance Status filter — Reject lists everything waiting to be fixed. A rejected row also shows **Resubmit** to exec and super_admin. The drawer opens from the row's View history button and shows only the history; the invoice file's View/Copy buttons are the Invoice Link column. Columns are defined as data in `columns.js` (`default` flags = the set everyone sees) and drawn by `InvoiceCell.jsx`; `ColumnManager` shows/hides them for the session only — nothing is saved. Dropdowns inside the sideways-scrolling table are not clipped because `CustomSelect` already anchors its list in a portal (Headless UI v2 `anchor`).

**Multi-vehicle invoices (MAIN-99).** One vendor invoice for work on many vehicles — hub greasing fifteen buses at a parking location — is recorded with **no ticket and no job card**. `batch_services` holds the supplier and the invoice file (on a job card the file lives on `job_cards.invoice_url`); `batch_service_vehicles` holds one line per vehicle **and kind of work** with its **site**. Site is per line because one invoice can cover buses from several sites: the form fills it from the vehicle's `vehicle_sites` links — fixed when there is one, a choice among them when there are several, any active site when there are none — and a saved site the bus has since left stays selectable. The database only requires that a site is present (`LINE_SITE_REQUIRED`), never that it is one of the vehicle's current sites: those links are rebuilt nightly, so that rule would make an old batch uncorrectable once its bus moved. The column is nullable for the prod→staging sync and enforced by the save function. The invoice is an ordinary `outsource_invoices` row with `batch_service_id` set instead of `job_card_id` (`outsource_invoices_one_owner_check` requires exactly one), so both statuses, the submission, the triggers, the summary tiles and the history work unchanged. Each batch has a running number, `batch_services.batch_number` (`GENERATED ALWAYS AS IDENTITY` like `job_card_number`; the prod→staging seed keeps prod's numbers, MAIN-139), shown as **MVI-12** via `src/utils/batchNumber.js` (MAIN-112). Pages: `/multi-vehicle-invoices/new` and `/multi-vehicle-invoices/MVI-12` (`BatchServiceDetail.jsx`), reached from "+ Multi-vehicle invoice" on the Job Cards and Invoices pages; the old `/batch-invoices/:id` links redirect (`LegacyBatchRedirect`). In the list a batch shows "MVI-12" / "N vehicles", and Vehicle History merges each vehicle's line in among its job cards.

Both tables have **SELECT policies only** (exec, super_admin, finance — the same people who can read job cards); every write goes through `save_batch_service_invoice(p_batch_id, p_batch, p_invoice, p_lines)`, which is `SECURITY DEFINER` with its own exec check as its first statement. That is what holds the rules no row policy can: the lines add up to the approved amount exactly (compared in `numeric`; the form uses paise via `src/utils/batchSplit.js`), no vehicle appears twice with the same standard work type, and **nothing changes once finance has accepted it** (it locks the invoice row first, so finance cannot accept it mid-save). Lines are matched on their `id` (a vehicle can have several), so an unchanged line writes no history. Its arguments after the id are `jsonb` — **do not add a parameter**, for the same overload reason as `save_purchase_invoice`. Changes to a batch's work details and lines are logged by `log_batch_service_change` under the batch's id and shown in the invoice history; `groupBatchLines` folds one save's line changes into a single entry. The list query keeps batches beside completed job cards by filtering the `job_card` embed to Completed and then `or(batch_service_id.not.is.null, job_card.not.is.null)` — PostgREST rejects `job_card.status` inside an `or()`. The invoice fields themselves are shared with the job card through `InvoiceDetailsFields.jsx` + `invoiceForm.js`.

**Work on each line (MAIN-112).** A line records its work as `work_type` (Greasing, Puncture, Air filling, Washing, Other — `BATCH_WORK_TYPES` in `src/constants/batchWorkTypes.js`, mirroring `batch_service_vehicles_work_type_check`), with `work_type_other` holding the text for Other, and its amount is `rate × quantity` (`batch_service_vehicles_amount_rate_check`; the save function computes it rather than trusting the client). A vehicle may appear once per standard type and any number of times as Other — `batch_service_vehicles_work_type_key`, a **deferred** partial exclusion constraint so a save can swap two lines' types. Any line may link `job_card_id`, and an Other line must; the save function (`OTHER_WORK_INCOMPLETE`, `JOB_CARD_MISMATCH`) requires the card to be an **outsourced** job card of the same vehicle — checked at save only, since a card's type can change later. The picker (`useOutsourceJobCardsForVehicles`) offers open cards, then those completed in the last 60 days, searchable by issue text via `SearchableSelect`'s `searchText`. The linked card may still carry its own invoice (see below), so the same work can be billed twice — an **accepted risk**: the job card page shows its own invoice and every linked line (`LinkedBatchInvoices`, exec/super_admin/finance only, since nobody else can read batches) side by side so the overlap is visible. The new columns are nullable for the prod→staging sync and enforced by the save function; `batch_services.description` was dropped.

**Cancelling and restoring a multi-vehicle invoice (MAIN-112).** `cancel_batch_service_invoice(p_batch_id, p_reason)` sets `batch_services.status = 'Cancelled'` with a required `cancel_reason` (plus `cancelled_at`/`cancelled_by`); it is refused while finance has the invoice Accepted or GST-closed (`BATCH_ACCEPTED` — finance moves it back to Hold first) and it **releases every job card link**, so a cancelled invoice never holds a job card back. `restore_batch_service_invoice(p_batch_id, p_links)` reverses it and, because the links were released, requires every Other line's outsourced job card again (`p_links: [{ id, job_card_id }]`). Both lock the invoice row. A cancelled invoice cannot be saved (`BATCH_CANCELLED`), drops out of `get_outsource_invoice_summary`, and stays in the list greyed with a Cancelled badge (`enrichInvoice` sets `cancelled`; finance controls are off for it). Status and reason go through `log_batch_service_change`, so the history drawer shows who cancelled or restored it and why. Separately, `guard_job_card_type_change` refuses switching a job card away from Outsource while any multi-vehicle invoice line links it; the job card page shows a lock instead of the edit pencil.

**Closing an outsourced job card without an invoice.** The card's own invoice (file + details) is optional. There is one close button: a card with a complete invoice, or with any multi-vehicle invoice line linked to it, closes as `Completed`; otherwise it closes as `Completed - Invoice Pending` and the exec finalizes it later — with its own invoice, or once an MVI line links it. Invoice details are all-or-nothing: once any field is typed the full set is validated, so half an `outsource_invoices` row is never saved. A linked card is never put in Invoice Pending (`close_job_card_with_scrap` refuses with `BATCH_LINKED`). The old `outsource_completion_requires_invoice` CHECK was dropped because a CHECK cannot see the link; `close_job_card_with_scrap` and `finalize_outsource_invoice` — the only paths to `Completed` — hold the rule. If the last link to a card that was completed without its own invoice goes away (line unlinked or removed, or the MVI cancelled, which releases every link), `batch_service_vehicles_demote_job_card` puts it back in Invoice Pending and writes an `audit_logs` row. It is a **deferred** constraint trigger so a save that moves a link between lines doesn't demote the card mid-transaction. Restoring an MVI does not promote the card back; the exec finalizes it.

### Supplier Ledger (MAIN-119)
`/supplier-ledger` (`SupplierLedger.jsx`, with the **Advances to repay** panel), `/supplier-ledger/SUP-5` (`SupplierStatement.jsx`) and `/supplier-ledger/advances/:person` (`AdvanceStatement.jsx`), for `finance`, `super_admin` (write) and `maintenance_exec` (read); reached from a dashboard tile and from Invoices. Finance pays suppliers against a running balance, not invoice by invoice. The flow it serves: a person (Manjunath, Gokilavanan, Nithin) or the NVS Maintenance account pays a vendor an advance upfront; the exec submits the invoice with that advance; accounts pays the supplier Approved − Advance and repays the advance to the person — so accounts' total outflow is the approved value and each person's balance keeps returning to zero.

**Paid By = repayment ledger names**: `Accounts` (company money, nothing to repay), `NVS 659 Manjunath`, `NVS 2954 Gokilavanan`, `PCN` (Petty Cash Nithin), `NVS Maintenance account`. So an advance and its repayment match by value, with no mapping table. Everyone but Accounts is repaid — NVS Maintenance account joined the people under MAIN-122. **Who is repaid is defined once, by `advance_people()`** (an immutable function returning them in display order), which `advance_ledger_lines()`, `supplier_ledger_lines()`'s `advance_by_person`, `get_advance_balances()`, `record_advance_repayment()` and the `advance_repayments_person_check` constraint all read; `ADVANCE_PEOPLE` in `src/constants/supplierLedger.js` mirrors it with display names. Adding a person is those two changes (and they must already be a Paid By option).

**A supplier's ledger** (`supplier_ledger_lines()`): every invoice finance has Accepted or GST-closed (Approved owed), its Advance as "Advance – <person>", vendor payments (`supplier_payments`, always `Bill accounted`, TDS allowed, cancelled with a reason, never deleted) and reconciliation adjustments. Invoice and advance lines are **derived** from `outsource_invoices` — moving an invoice back to Hold or on to Reject takes it out, and MAIN-118's lock keeps its amounts fixed while it is in. Each invoice line shows its split (`invoiceSplit`). **A person's ledger** (`advance_ledger_lines()`): the advance on each accepted invoice whose Paid By is theirs, and repayments (`advance_repayments`, no TDS). Balances start at zero.

**Order and dates — two different clocks.** Statements are in **recording order by timestamp**, as Tally orders them, with no ordering by kind: an invoice and its advance at `outsource_invoices.accepted_at` (stamped by `outsource_invoices_stamp_accepted_at` on entering Accepted, kept through a GST close, cleared on leaving), a payment when it was recorded (its date paid is shown in the line), an adjustment at the end of its as-of day or when it was posted, whichever is earlier. **Due dates** count from the day the invoice reached finance (`submitted_on`) + the supplier's credit days — finance taking time to accept moves nothing. People have no credit days.

**Wednesday runs.** Finance releases payments every Wednesday — **fixed in code, not a setting**: `payment_run_for()` (mirrored by `src/utils/paymentRuns.js`) moves a due date to the first Wednesday on or after it; an amount is **overdue** once its run has passed, else due this Wednesday, next Wednesday or later. `supplier_open_items()` / `advance_open_items()` allocate credits to the earliest-due owed lines first, for these figures only — nothing is stored against an invoice. Credit days are `suppliers.payment_terms_days`, an integer (blank = 0), set through `set_supplier_credit_days` (logged to `audit_logs`); finance has no UPDATE on `suppliers`. The registration form takes it as a number (0–365).

**Reconciliation** (`supplier_ledger_adjustments`) is stock-audit style: finance enters the balance confirmed against Tally or the vendor's statement as of a date; `reconcile_supplier_balance` freezes the app's figure over everything recorded up to the end of that day (or now) and the generated `amount` is the difference. A zero difference is still recorded as "last reconciled". `reverse_ledger_adjustment` undoes one with a reason; it stays on the statement struck through and out of every total.

All ledger tables have **SELECT policies only**; every write goes through a `SECURITY DEFINER` function that calls `assert_ledger_writer()` (finance/super_admin) and locks the supplier row (repayments take an advisory lock per person). Reads go through `get_supplier_balances` / `get_supplier_statement` / `get_supplier_open_items` and `get_advance_balances` / `get_advance_statement` / `get_advance_open_items`, which check for exec/finance and attach performer names. The Invoices list sorts newest submitted first. Removing the now-unused Pay By Date is MAIN-121.

**Split by company (MAIN-162, epic MAIN-154).** Each company owes its suppliers and repays its people separately, as Tally keeps them. The page has two tabs, **NVS Travels** and **NVS Travel Solutions Pvt Ltd**, carried as `?co=nvs-travels` / `?co=nvs-travel-solutions` on all three addresses (`ledgerCompanyFrom`, `withLedgerCompany`, `src/utils/ledgerCompany.js`; no `co` = NVS Travels, so old links still open). An invoice and its advance belong to `outsource_invoices.company` (MAIN-161); `supplier_payments`, `advance_repayments` and `supplier_ledger_adjustments` store their own `company` (everything before was NVS Travels). `supplier_ledger_lines()` / `advance_ledger_lines()` return `company`, and every figure — balance, Wednesday buckets, open items, running balance, awaiting acceptance — is per supplier (or person) **and** company, so a payment in one company never clears the other's invoice. Every reader takes `p_company` first (`assert_ledger_company`); so does `reconcile_supplier_balance`. `record_supplier_payment` / `record_advance_repayment` read `company` from `p_payment` — **do not add a parameter**. The payment, repayment and reconcile forms show the tab's company fixed (`CompanyLine`) — user decision: one recorded under the wrong company is cancelled with a reason and recorded again on the right tab. Credit days stay per supplier, shared by both companies. Every approved supplier and all four people appear on both tabs.

### Company ledgers (MAIN-156, epic MAIN-154)
`/company-ledger/nvs-travels` and `/company-ledger/nvs-travel-solutions` (`CompanyLedger.jsx`; `/company-ledger` redirects to NVS Travels), read for `maintenance_exec`, `super_admin` and `finance`, reconciled by `finance`/`super_admin` (below); reached from a dashboard tile and from Supplier Ledger. **Nothing is stored but reconciliations:** `company_ledger_lines(p_company)` (service-role only) derives every line, and `get_company_ledger(p_company)` (`SECURITY DEFINER`, exec/finance check) adds the running columns — so nobody can edit a line and the prod→staging seed needs nothing.
- **Lines:** purchases and refurbishments by `billed_to` (`pi.total_amount`; GST from the lines); job card and multi-vehicle invoices by `outsource_invoices.company` (Approved Amount; cancelled MVIs out); vehicle sales from `vehicle_company_changes` (kind `sale`), in **both** ledgers the opposite way round, GST = value × % ÷ (100 + %); spare transfers and their reversals from `spare_transfers` (MAIN-159, above). Spares used on an in-house job card are **not** an entry — the stock was counted when bought.
- **Two running columns, never added together:** `spent_to_date` (purchases + invoices ± spare transfers) and `owed_balance` (between the companies; positive = the other company owes this one). A vehicle bought from the other company is owed, not spent (user decision 2026-11-25); a spare transfer moves both.
- **An invoice enters when finance accepts it** (Accepted or either GST close, at `accepted_at`), as in the supplier ledger. **A purchase counts once** — the purchase line, never also its finance invoice; with no finance invoice it was recorded before MAIN-129 and counts from `created_at` with GST status Unknown.
- **GST status** per line: Claimed (GST reconciled & closed), No GST (GST not applicable & closed), Not yet reconciled (Accepted), Unknown (pre-MAIN-129 purchase), Inter-company (sales). Job card and multi-vehicle invoices count their GST breakdown's total × Approved ÷ Invoice Value (MAIN-166, see Invoices); one without a breakdown has `gst` NULL and reads "Not recorded". The "GST in spending" tile leaves out the GST on vehicle sales but counts a spare transfer's, signed.
- **PI-176, PI-180, PI-183, PI-185** ("Bannerghatta Hub", ₹192) were workshop moves recorded as purchases and are left out, by number, in `company_ledger_lines`.
- Display and totals (in paise) are in `src/utils/companyLedger.js` (tested); export in `companyLedgerExport.js`.

### Labour and the activity complete date (MAIN-116)
Who worked on an **in-house** work item, and for how long, lives in `issue_labour` (`issue_id`, `technician_id`, `hours`): one row per person per item, `0 < hours ≤ 24`. `guard_issue_labour` only accepts an active `mechanic`/`electrician`, and only on an item of an In-house job card. Only exec/super_admin write it (`"Execs manage issue labour"`); finance reads it; a technician reads their own rows, and through `has_labour_on_job_card()` the cards, issues and parts they worked on. Every add/edit/remove is written to `audit_logs` by the `issue_labour_audit` trigger as an `issues` UPDATE keyed by the ticket with a single `labour` field — the shape `TicketTimeline` already renders — so the hooks in `useIssueLabour.js` do not log it themselves.

`issues.labour_hours` is the **pre-MAIN-116 value with no person attached**. Nothing writes it any more; `issueLabourHours()` in `src/utils/labour.js` shows it as "Unattributed" on an item with no `issue_labour` rows and ignores it once anyone is added. Use that helper (and `totalLabourHours`) for any labour total so old hours keep counting.

`issues.completed_on` is the **activity complete date**: `set_issue_completed_on` stamps today (IST) when an item reaches Done, clears it when it leaves Done, and refuses a future date; the exec can change it from the work item header. Labour analytics place hours by this date. It was backfilled from `job_cards.completed_at` — nothing ever recorded when an individual item was marked Done.

Switching a card In-house → Outsource deletes its labour in the same statement (`clear_labour_on_outsource`); the app's confirmation names the hours and people first. The single **Assigned** mechanic chip is gone (0 of 3,265 in-house cards in prod ever had one). `job_cards.assigned_mechanic_id` and its `"Mechanics … assigned cards"` policies are kept, unused, until a cleanup drops them together.

### UI conventions
- **No browser pop-ups (MAIN-144).** `alert()`, `confirm()` and `prompt()` freeze the whole page — and automated testing on staging — until someone clicks OK, so none are left in the app; don't add one. Use `useToast()` / `useConfirm()` from `src/hooks/useFeedback.js` (provider: `FeedbackProvider` in `src/components/shared/Feedback.jsx`, mounted once in `App.jsx` above the router, so a message survives the navigation after a save):
  - **Success** → `toast.success(…)`, fades after 4 s. **Error** → `toast.error(…)`, stays until closed; keep the server's message in it.
  - **Form checks** (a missing or out-of-range field) → red text next to the field, cleared on the next edit — not a toast. `invoiceForm.js` / `InvoiceDetailsFields` and `IssueWorkCard` are the pattern.
  - **"Are you sure?"** → `if (!(await confirm({ title, message, confirmLabel, tone }))) return` — styled like `RejectInvoiceModal`; `tone: 'danger'` (default, red) for anything destructive, `'primary'` otherwise. Esc and the backdrop count as Cancel. With `reason: { label, required? }` it also asks for a reason and resolves to the text, or `null` when cancelled (Stock Audit's Cancel count).
  - A **new or reset password** is never a toast: Add User / Edit User hand it to User Management, which shows `PasswordPanel` (Copy button) until it is closed.
  - A component test that renders something using these hooks must wrap it in `<FeedbackProvider>`.
- **No native `<select>` (MAIN-145).** `CustomSelect` in forms, modals and tables; `FilterSelect` in filter bars. `CustomSelect` matches the selected option with `opt.value || …`, so it cannot show a value of `0` as selected — give it string values and convert on change, as the purchase and refurbishment GST dropdowns do.
- **Password boxes use `PasswordInput` (MAIN-146)** — the eye button, hidden by default. Add User / Edit User have their own toggle (shown by default, with Generate and Copy).

### Dates and time zones
The business runs on Indian time (IST, UTC+5:30); the database runs with `TimeZone = UTC`. The schema mixes two kinds of timestamp, and confusing them has cost real mistakes (MAIN-83, MAIN-163, MAIN-171 — and a figure of 1,208 that was really 1):
- **`timestamp without time zone`, holding UTC:** `tickets.created_at`, `issues.created_at` / `rated_at`, `job_cards.created_at` / `completed_at`, `issue_parts.added_at`, `purchase_invoices.created_at`, `stock_audits.*_at`, `stock_transfers.transferred_at`, `parts`, `users`, `vehicles`, `sites` and most other `created_at`s on older tables.
- **`timestamptz`:** the newer ones — `tickets.resolved_at` / `closed_at` / `rejected_at` / SLA deadlines, `issues.completed_at`, `outsource_invoices.*_at`, `vehicle_company_changes.created_at`, `opening_stock_lots.created_at`, every ledger table.
- **Check `information_schema.columns.data_type` before any time-zone arithmetic.** `AT TIME ZONE` does opposite things on the two types.

In SQL:
- IST date of a zone-less (UTC) column: `((col AT TIME ZONE 'UTC') AT TIME ZONE 'Asia/Kolkata')::date`. Never `col::date` — that is the UK date, and anything raised 00:00–05:30 IST lands on the previous day.
- IST date of a `timestamptz`: `(col AT TIME ZONE 'Asia/Kolkata')::date`.
- **Never compare, `coalesce`, `least` or cast between the two kinds without saying which zone the zone-less one is in** (`col AT TIME ZONE 'UTC'`). An implicit comparison or `::timestamp` cast uses the session time zone and is right only while that is UTC (MAIN-171 fixed `job_card_invoice_company` and `part_cost_lots`).
- Filtering a zone-less column from the browser: send UTC instants (`localDayRangeToUtc`) — Postgres silently drops a `+05:30` offset compared with `timestamp without time zone` (MAIN-83).

In the browser:
- Show any timestamp through `toDate` / `formatDate` / `formatDateTime` (`src/utils/datetime.js`): a zone-less value arrives without a `Z`, and plain `new Date()` would read it as local time, 5½ hours early.
- A figure that must equal a database IST-day figure buckets by IST explicitly (`istDayOf` / `istToday` in `maintenanceCost.js`, `entryIstDay` in `companyLedger.js`), never by the browser's day (`dateKey`, `entryDay`).
- Tests run with `TZ=UTC`, as CI does; a day-bucketing test should pass under both `TZ=UTC` and `TZ=Asia/Kolkata`.

**Before reporting any date-based figure, sanity-check it against how the workshop runs (tickets are raised about 06:00–23:00 IST) and get it two independent ways** (e.g. `AT TIME ZONE` and a plain `col::time >= '18:30'` count).
